# EE-Req Manager 汽车需求工程框架

## 1. 产品中心

Requirement 是配置和评审的中心对象。功能、ECU、接口信号、测试与证据是需求的下游架构对象；它们必须通过类型稳定、可审计的 TraceLink 连接，而不是只靠文档描述。

## 2. 最小需求属性

每条工程需求至少应明确：编号、类型、正文、上游来源、状态、负责人、验证方法和验收准则。安全需求还应记录来源安全目标、ASIL、故障或功能不足条件、时间约束、安全/降级状态和恢复条件。

需求正文优先采用：

```text
在【条件】下，当【触发】发生时，【主体】应在【时间】内执行【可观察行为】，并满足【量化边界】。
```

验收准则优先采用：

```text
给定【初始状态】，当【输入/事件】发生，则【输出/状态】满足【数值、单位、容差和时限】。
```

## 3. 质量门禁

- 明确义务：使用“应/shall/must”，避免把说明性文字当作需求。
- 原子性：一条需求承载一个可独立分配、变更和验证的主要义务。
- 无歧义：避免“尽快、适当、正常、友好、必要时”等未定义词。
- 可验证：有验证方法、可执行验收准则，并在适用时包含数值、单位、容差与时间。
- 可追踪：有上游来源；工程需求有架构分配；已批准需求有验证链路。
- 可审计：修改原因、字段级变更和基线快照可重建当时状态。

规则评分只判断文本和属性完整性，不判断技术方案是否正确。

## 4. 推荐追踪链

### 通用 E/E

利益相关方需求 → 整车需求 → 功能/系统需求 → 逻辑功能 → ECU → 接口/信号 → 验证需求/测试。

### 功能安全

HARA/危险事件 → 安全目标 → FSR → TSR → HSR/SWR → 安全机制 → 验证证据。

### Automotive SPICE

利益相关方需求 → SYS.2 → SYS.3 → SWE.1 → SWE.2 → SWE.3 → SWE.4/5/6。

### SOTIF

预期功能/ODD → 功能不足 → 触发条件 → 危险场景 → 风险降低措施 → 场景验证 → 残余风险论证。

## 5. 评审边界

EE-Req Manager 可以生成结构、检查缺口和保存证据索引，但不能声明项目“符合”或“通过”某项标准。合规结论必须由组织流程、授权标准文本、适用性分析、独立评审和客观证据共同支撑。
