# 开源技术路线与边界

## 目标架构

```text
需求规范与追溯（StrictDoc 思想）
              │
              ▼
Python 领域服务 ── SQLAlchemy ── SQLite
      │                         │
      ├── cantools：DBC 精确解析 │ 项目隔离 / 审计 / 基线
      └── canmatrix：多格式归一化与版本比较
              │
              ▼
React Flow + ELK：可编辑 ECU—信号—ECU 数据流
```

## 不变的工程原则

1. 需求是首要受控对象；功能、ECU、接口信号和验证是可追溯对象，不以图代替需求证据。
2. 所有业务查询、修改和审计必须带 `project_id`，禁止跨车型串数据。
3. DBC/通信矩阵是接口事实来源；项目内人工修改作为覆盖层保存，不回写并污染原始导入证据。
4. 多接收节点使用一条信号对应多个 Rx 端点，不把它压缩成单值字段。
5. 图上每次新增、移动、删除和恢复都进入变更记录，必须保留修改原因。

## 分阶段路线

### 阶段 1：开源基础（当前）

- cantools 继续负责生产 DBC 导入，保留精度、偏移、范围、字节序和枚举。
- canmatrix 提供通信矩阵版本比较，先支持其稳定的 DBC/XLSX/DBF/SYM/JSON 适配器。
- React Flow 接管交互画布，ELK 负责自动排版；Python/SQLite 仍是唯一业务事实源。
- 建立第三方依赖和许可证清单。

当前“信号数据流图”已不依赖公网 CDN；旧的功能关系图与 Excel 预览仍使用 vis-network，列入后续本地化迁移范围。

### 阶段 2：需求交换与评审

- 按 StrictDoc 的思想补齐需求类型、字段 Schema、层级校验和可配置视图。
- 增加 ReqIF 导入/导出适配层；导入先进入预览和冲突检查，不直接覆盖受控需求。
- 把通信矩阵差异关联到受影响的接口需求、功能和验证项。

### 阶段 3：工程协作

- 从单文件 SQLite 演进到可选 PostgreSQL；保留离线单机模式。
- 引入乐观锁/对象版本号、评审工作流和基线间差异。
- 提供稳定 API，使外部 CI、测试平台和 PLM/ALM 能按对象编号同步。

## 为什么不直接合并 StrictDoc 源码

StrictDoc 是完整的文档式需求工具，而本平台的核心是汽车 E/E 车型、功能、ECU、CAN 信号和图形化数据流。当前采用其可验证、可追溯、文档层级清晰的设计思想，保留自己的领域模型；以后通过 ReqIF/导入适配器互操作，比复制内部实现更容易维护和升级。
